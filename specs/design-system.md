# Design system (binding spec)

The binding look-and-feel spec, plus the z-index scale, hover-popup primitive,
and sticky-chrome stacking. The token catalogue is also viewable live in-app via
the `#design` route ([`DesignSystem.jsx`](../src/components/DesignSystem.jsx)).

## The UI look is a shared token module (light glassmorphism, monochrome), not per-component classes

The app's cosmetic classes live in one place — [`src/design/designSystem.js`](../src/design/designSystem.js) — and are consumed across the UI (`App`, `EventsView`, `RosterSlotPill`, the modals, the stats panel, etc.). It exports Tailwind class-string tokens in three families: a **3-tier typography hierarchy** for *chrome* (`tierTitle`, `tierSection`, `tierLabel`, `tierUnit`, plus `headingPage`/`headingModal` for larger titles and `helperText` for prose); **glass surfaces** (`glassPanel`, `glassCard`, `glassPopup`, `glassArrow`, `glassMenu`, `glassModal`, `modalBackdrop`, `glassFab`); and **controls** (`btnPrimary`, `btnNeutral`, `btnDanger`, `monoChip`, `hoverRow`, `tabActive`, `tabInactive`). Rationale: the same strings had been copy-pasted across many files, so a tweak in one place drifted from the others; centralizing them keeps the look consistent and tunable in one edit.

**Tokens over hand-rolled classes (binding).** Surfaces, buttons and chips must consume the tokens, not re-write the recipe inline. A glass panel is `glassPanel`/`glassCard` (never a hand-written `bg-white/40 backdrop-blur-md … border border-white/30 shadow-lg`); a primary/neutral/destructive button is `btnPrimary`/`btnNeutral`/`btnDanger` (never a bare `bg-gray-800 …`/`bg-white hover:bg-gray-50 …`/`bg-red-600 …`); a small neutral chip is `monoChip` (never opaque `bg-gray-100`/`bg-gray-200`). The pinned **draft ("N unsaved changes") bar** is the one deliberate exception to "warnings are near-glass tints": it is the highest-urgency chrome (act now — Save or Discard), so it uses a **saturated** amber fill — and that recipe is itself a token (`draftBar`). Its **Save button keeps the saturated amber CTA** (`bg-amber-600`) and Discard the amber-outline ghost — deliberately *not* the monochrome `btnPrimary`/`btnNeutral`, because the whole bar is the app's single "shout" surface and a grey Save button read as demoted against the amber. This is the one place a coloured CTA is allowed. Opaque `bg-gray-50`/`bg-white` fills are disallowed — even the loading screen and in-modal wells are translucent — so nested panels never turn the glass muddy grey. **Modals share one padding scale** (`p-4 sm:p-6` body, `px-4 sm:px-6 py-3 sm:py-4` header) so they don't drift between `p-5`/`p-6`/`p-4`. **Repeated markup is extracted into shared primitives in `SharedComponents.jsx`** — `IssueSummary`, `StatTile`, `ModalHeader`, `ModalCloseButton`, `GlassFab`, and a `useClickOutside` hook — so the FABs, stat tiles, modal chrome and click-to-open dropdowns are defined once. Rationale: the audit found the same glass/button/chip strings re-typed with small drifts (radii, opacities, hover colours); routing everything through tokens/primitives removes the drift and makes a restyle a one-file change.

**Design system is guarded by a lint test and documented by a living page (binding).** The repo has no ESLint, so the token discipline is enforced by a dependency-free Vitest guardrail (`src/design/designSystem.lint.test.js`) that scans `src/` and fails if any file (a) inlines an exact glass-token string (`glassPanel`/`glassCard`/`glassMenu`/`glassModal`/`glassFab`/`draftBar`) instead of importing it, or (b) uses a banned decorative hue (`yellow-*`, which warnings were unified off of). It is intentionally **high-signal, not exhaustive** — it flags unambiguous copy-paste/hue mistakes rather than every raw utility, so it never fights the legitimate one-off surfaces (hover states, the dark log console, the day-pill scroller). Two files are allowlisted: `designSystem.js` (defines the tokens) and `DesignSystem.jsx` (renders them verbatim). Rationale: a broad "ban all raw `bg-white/`/`backdrop-blur`" rule flagged dozens of intentional surfaces and would have been silenced; catching the exact recipe-duplication is what actually preserves the "one edit restyles everything" property. The companion **living reference page** (`src/components/DesignSystem.jsx`, reached via the `#design` URL hash — no router, no auth, gated at mount in `main.jsx` so `Root`'s hooks are never conditionally skipped) renders every token and shared primitive so new work has a visual source of truth.

**Colour policy (binding).** Three categories, treated differently:
- **Decorative** accents were monochromatized to slate/gray. Blue is *no longer a brand hue* — the active tab, date/day/reminder chips, dropdown hovers, drag-over rings, modal CTAs, the generation-result stat tiles, and the `generation`/`swap` log chips were all recolored to gray. Do not reintroduce decorative blue/green/purple.
- **Semantic** colour is KEPT (it carries meaning) but rendered **accent-only** on glass so it never shouts against the translucent UI: instead of saturated fills (`bg-red-100`, `bg-yellow-100`, `ring-2 ring-red-500`), semantic surfaces use a near-glass tint + a thin `border-l-2` accent + muted `-700` text (tokens `semanticError`/`semanticWarning`, chips `errorChip`/`warningChip`, soft `ring-1` card rings `ringError`/`ringWarning`). red = error / destructive, amber = warning / unsaved draft, and the diff triad emerald = added / amber = changed / rose = removed. **Warnings are unified on `amber`, not `yellow`** — amber is warmer, softer against the glass, and matches the draft bar + the diff "changed" hue; do not reintroduce yellow. The action-log chips for delete/insert/update were aligned to the same triad (rose/emerald/amber).
- **Functional** role/day colour (`colorUtils.js`) is KEPT but *muted*, and expressed as **coloured text with a neutral (never coloured) surface**. `COLOR_PALETTE` is a list of **text-colour-only** classes (`text-purple-600`, …). Role *tags* (roster slot pills, member-card role/understudy tags) render the label in its role hue inside a **subtle neutral outline** — `border border-gray-200/70 bg-white/30 rounded` — so the tag still reads as a pill but the *colour* is only in the font, not a filled background; understudy tags additionally use a **dashed** border as a non-colour cue. Inline role labels (availability breakdown, the add-role menu item) are bare coloured text. The event **day-of-week label** is text-colour only (`DAY_CARD_COLORS`). **Availability is shown by the ✓/✗ glyph plus lightness, not hue** — the eligible-but-unassigned name is neutral `text-gray-700`; the **unavailable name is strongly *muted* (`text-gray-300`)** so it recedes, not red-and-struck-through. Rationale: red pulled the same danger hue as real errors/clashes and the strikethrough made a long roster list look noisy; a muted-vs-full-weight contrast reads as "dimmed = can't, normal = can" at a glance and the ✓/✗ glyph already carries the state, keeping the list monochrome. The **assigned member is emerald** — both the left ✓ and the name (`text-emerald-600`), no separate second marker. Emerald is the palette's "added/positive" hue (the diff-added colour), so the whole row reading green says "this person is in", consistent with the rest of the scheme; the role labels in this breakdown reuse the **same outlined coloured-font tag** as the roster slot pills (`border border-gray-200/70 bg-white/30 rounded px-1.5 py-0.5 text-xs`) so the dropdown matches the card above it. Hue distinguishes roles/days at a glance while every surface stays monochrome, matching the roster-stats look. Monochromizing hues entirely was rejected (loses at-a-glance identification); a coloured *fill* was rejected (saturated pills fight the glass). **Members view and Events view share one look** (`p-4 sm:p-6`, the same `bg-white/40 backdrop-blur-md` card, `headingPage` title, outlined coloured-font tags, no emojis); the members role-filter buttons are neutral glass chips whose only colour is the role label text. **All in-modal surfaces are glass, not opaque grey** — the generation-result quality metrics use `glassCard` (translucent), never `bg-gray-50`/`bg-white`, so nested panels don't turn the glass modal muddy grey.

**Event-card section order & separators (binding).** The card is split into two groups. **Original event configuration** comes first — the **Roster** (row assignments) followed immediately by the **Reminder** note — with **no divider between them** (they describe the same configured event) and no divider above them (the header is the top). Everything below is **derived / computed, not part of the configured event**: the **Availability Details** and then the **Validation messages** (errors/warnings), wrapped together in one `mt-auto pt-3 border-t border-gray-200` group. The `mt-auto` **flushes the derived group to the bottom of the card** so, across the equal-height CSS-grid row, every card's "Availability Details" toggle and validation messages line up along the bottom instead of floating mid-card. The single `border-t` on that wrapper marks the one meaningful boundary — config vs. derived. The **Availability Details toggle uses the uppercase tracked chrome type** (`tierSection`), matching the "ROSTER" label and the member-card section toggles. The event card root is `h-full flex flex-col` for the flush to work. The derived sections share the group, so there is **no divider between availability and validation**; they separate with plain spacing (`mt-2`). **Validation is kept last** so the computed errors/warnings land at the very bottom. Rationale: a divider per section was visual noise ("why so many dividers?"); the only boundary worth drawing is the conceptual one between what a user *configured* (roster + reminder) and what the system *computed* (availability + validation). Within the Availability breakdown, per-role blocks are separated by **spacing only, no divider** (`mb-4`) — a border between blocks was tried but abandoned because CSS `columns` masonry can't drop the rule at a column top (`first-child` only clears the very first block, leaving a stray line atop the second column), and the whole point of grouping here is subtle. With no border, plain vertical spacing reads cleanly, so the breakdown stays on simple CSS `columns` masonry (`columns-2` + `break-inside-avoid`) rather than a manual two-column grid.

**Member card: note + unavailability calendar (binding).** A member constraint (`member_constraints[]` entry) may carry a free-text `note` (e.g. `note: No Sundays`) alongside `unavailable_dates`. That `note` is parsed but was historically *dropped* at the UI layer; it is now surfaced on the `MemberCard` in the **same soft grey box as the event reminder** (`text-xs text-gray-600 bg-gray-100/70 px-2 py-1.5 rounded border border-gray-200/60`), placed **after the role/understudy tags** (a note like "no Sundays" qualifies the roles above it) — a member's note and an event's reminder are the same kind of "human aside", so they share one treatment. The **Telegram handle is de-emphasised** (`text-xs text-gray-400`, no "Telegram:" label) so it recedes below the name. The card's collapsible section labels (**Unavailable**, **Preferences**) use the shared **uppercase tracked chrome type** (`tierSection`), matching the "ROSTER" label on event cards; only the trailing count keeps `normal-case`. That footer group is **flushed to the bottom of the card** (`mt-auto`, card root `h-full flex flex-col`) so the toggles line up along the bottom across the equal-height grid row instead of floating right under a variable number of role tags. **The Unavailable section is *always* rendered** — mirroring the always-present event "Availability Details" — so it consistently anchors the bottom of every card; when the member has no unavailable days it shows a non-interactive `Unavailable (none)` label (disabled toggle, arrow hidden) rather than disappearing. Preferences stays conditional (an optional extra), rendered below Unavailable when present. **Unavailability is shown as a compact per-month calendar, not a flat list of date ranges.** `unavailable_dates` is polymorphic (single `YYYY-MM-DD` strings and inclusive `{start,end}` ranges); the pure helpers in `calendarUtils.js` (`expandUnavailableDays` → `monthsFromDays` → `monthGridCells`, unit-tested) expand it into concrete days and group them by month. `MemberCard` renders **one `MonthCalendar` grid per month that contains an unavailable day** (no empty months, no arbitrary navigation) — a deliberately *tight* Sunday-start 7-column grid (`aspect-square` cells, `text-[11px]` day numbers, `gap-px`) where unavailable days are shaded muted slate (`bg-slate-500/70`, matching the monochrome availability cue used elsewhere) and all others are plain neutral text. Rationale: a list of 13 dates (a member out every Sunday) is unreadable; a calendar makes the *pattern* obvious at a glance, and keeping the cells small stops a multi-month member from dominating the card. (An `items-start` grid — letting an expanded card size to its own content instead of stretching row-mates — was tried and reverted: the ragged, misaligned card tops looked worse than a little empty space, so the Members grid keeps equal-height rows.) Day keys are built from the string's parts (`parseDayKey`), **not** `new Date(str)`, so a UTC-midnight parse can't shift a day backwards in a negative-offset timezone. `MemberCard` and its `MonthCalendar` live in their **own `MemberCard.jsx` module**, not `SharedComponents.jsx` — they are members-domain UI, whereas `SharedComponents.jsx` is reserved for app-wide primitives/hooks (`HoverCard`, `GlassFab`, `useClickOutside`, …). Keeping domain components out of the "shared" file stops it becoming a grab-bag.

**Card status vs. day cue (binding).** Event cards are a neutral monochrome glass surface. The **day of week is conveyed only by a faint accent hue on the day-label text** (`DAY_CARD_COLORS`, e.g. `text-purple-500`) — *not* by a card border. **Status is shown by a coloured top-right CORNER wedge** (`StatusCorner` in `EventsView.jsx`): a small rotated-square, red = error / amber = warning. No corner appears when the event has no issues. Rationale: a full coloured ring/stripe per weekday competed visually with the error/warning signal, so "which day" (text hue) and "is there a problem" (corner accent) are kept as separate cues. The earlier status treatment was a full-height `border-l-4` left stripe; it was replaced by the corner wedge because a corner is a smaller, more contained mark than a coloured bar running down the whole card. The wedge sits **top-right, not top-left** — the card's header text (date + day) reads left-to-right from the top-left, so a top-left wedge crowded it; the top-right corner is empty, so the status mark lands there without fighting the title. **The wedge clips itself** (its own `overflow-hidden rounded-tr-lg` 28×28 box) — the **card is deliberately *not* `overflow-hidden`**. This is load-bearing: an `overflow-hidden` card would also clip inline dropdowns (the assignment picker, which is `absolute top-full` and can extend below the card), cutting them off at the card's edge. Clipping only the wedge lets the card stay overflow-visible so popovers spill out; the `rounded-tr-lg` must match `glassPanel`'s `rounded-lg` so the wedge still hugs the rounded corner. (Popover *stacking* above sibling cards is a separate concern, handled by lifting the open card to `zPopover` via `onOpenChange` — see events-ui.)

**No decorative emojis (binding).** Decorative emoji glyphs (❌ ⚠️ ℹ️ ✨ 📄 🧹 📋 💾 ⭐ etc.) were removed app-wide — they read as cheap against the clean glass look. Status is carried by the accent-only semantic tokens and short text labels ("Error:", "Warning:", the "Auto"/`{ }` FAB labels) instead. *Functional* monochrome typographic marks are kept: availability ✓/✗, the assigned bold ✓, undo/redo ↶/↷, and the ▼/▶ disclosure arrows are structural UI, not decoration.

**Validation summary is dots + numbers, not a pill (binding).** Both the Events and Members headings present errors/warnings the same way via a single shared `IssueSummary` component (`SharedComponents.jsx`): coloured dot(s) + count(s) (red = errors, amber = warnings) followed by a ▾ caret. **Clicking** the caret toggles a glass dropdown listing each issue (no hover — hover was replaced so touch works and the two surfaces behave identically); clicking outside closes it. There is no chip/pill background. Rationale: a filled pill reintroduced a saturated surface the colour policy avoids, and the old full-width amber `WarningBanner` on the members view was inconsistent with the events summary — both now use the one component.

**Swap confirmation is a two-row before→after card (binding).** The staged-swap dialog (`pendingSwap` in `App.jsx`) renders the two affected slots as two glass rows, each captioned `date · role` (uppercase chrome) with the occupant shown as `before → after` (old name struck through, new name bold). The earlier prose form ("Swap X ↔ Y?" plus a redundant past-tense "Swapped …" sentence) was replaced because it duplicated information and read as an announcement of something already done rather than a confirmation.

**Calibrated decisions that must not be tuned away blindly:** (1) **Tier 1 uses `tracking-wide` (0.025em), not `tracking-[0.2em]`** — at the title's small size very wide letter-spacing left distracting gaps between letters, so hierarchy is carried by weight + size, not extreme tracking; (2) **`helperText` is a muted `text-gray-400`** (an earlier `text-gray-300` pass was too faint to read) — descriptive, sentence-form prose (which is *not* uppercase/thin, unlike chrome labels) should recede behind the data and the labelled chrome. **Data supplied by the YAML (member names, role names, numeric values) is NOT chrome** and stays normal-case; it must not adopt the uppercase tier tokens. See also the quality-metrics presentation decision in [data-layer.md](data-layer.md).

## Z-index is a single named scale

Stacking order is governed by five named tokens in `designSystem.js`, not ad-hoc `z-*` values: `zInCard` (`z-10`) < `zSticky` (`z-30`) < `zPopover` (`z-40`) < `zToast` (`z-[45]`) < `zModal` (`z-50`). **Rule: a layer that opens *on top of* another must sit on a higher rung.** Rationale: an events warnings/error dropdown (`zPopover`) was opening *underneath* the sticky select toolbar because both were hand-set to `z-40`; without a named ladder these collisions are invisible until something overlaps wrong. In-card controls use `zInCard`; sticky chrome (draft bar, tab switcher, select toolbar, month selector) uses `zSticky`; popovers/menus/hover cards use `zPopover`; transient toasts use `zToast`; confirmation modals and drawers use `zModal`.

## Hover popups have one shared behaviour — the `HoverCard` primitive

All hover-triggered popovers (the Auto-button algorithm explainer, the unsaved-changes diff-dot tooltip) go through one primitive: [`HoverCard`](../src/components/SharedComponents.jsx). It exists because hand-rolled hover popups each re-invented the same broken behaviour — most visibly, moving the mouse from the trigger toward the popup crossed a dead gap and dismissed it. `HoverCard` guarantees: (1) trigger and panel share one hover region with a small close **delay** (`CLOSE_DELAY_MS`, cancelled if the pointer re-enters either) so you can travel to the panel and scroll it; (2) on touch devices it is **tap-to-toggle** and closes on outside-tap/Escape (the `tapToggles` prop is set false where the trigger has its own tap action, e.g. the Auto FAB, so the explainer is desktop-hover-only there); (3) it accepts a `placement` and content, so callers never position popups by hand.

**The panel is portaled to `<body>` — this is load-bearing, not incidental.** `position: fixed` is resolved against the nearest ancestor that establishes a *containing block*, which includes any ancestor with a `transform` **or** a `backdrop-filter`. The glass tokens (`glassPanel`/`glassCard`) use `backdrop-blur` (i.e. `backdrop-filter`), so a `fixed` popup rendered inside a glass card was being positioned relative to that card, not the viewport — the diff-dot tooltip "didn't appear next to the dot". Rendering the panel through `createPortal(..., document.body)` escapes those containing blocks so viewport coordinates mean what they say. Because the panel then lives outside the trigger's DOM subtree, the outside-click handler must treat clicks inside the portaled panel as "inside". **Reliability note:** because the panel is portaled, on the first layout pass after opening its ref can be unattached or its `offsetWidth` still `0` (not yet painted). The panel starts at `visibility: hidden` until a valid position resolves, so if that first measurement is skipped the panel silently *never appears* ("the orange dot popup still doesn't show next to my hover"). `reposition` therefore **re-schedules itself via `requestAnimationFrame` while the panel has no size**, and the pending frame is cancelled on close/unmount — guaranteeing `pos` resolves and the panel becomes visible next to its trigger.

**Popup position is measured and clamped to the viewport dynamically, not with static offset classes.** `HoverCard` measures the trigger and panel on open (and on scroll/resize) and computes `fixed` coordinates that (a) **flip** to the opposite side when the preferred side lacks room, (b) **clamp** the cross-axis so the panel never spills past an 8px viewport margin, and (c) cap the panel's `max-height` to the available space with internal scroll — so a tall explainer stays scrollable and a popup near the screen edge is fully visible. It also supports an `align` prop (`center` vs `start`) so a wide panel triggered by a tiny anchor (the diff dot) can align its edge to the anchor instead of centering off-screen. Rationale: earlier popups used fixed `left-1/2 -translate-x-1/2` classes that couldn't react to the trigger's real position, so cards near the left edge or long algorithm text overflowed the window. Panels also carry a `max-w-[calc(100vw-1rem)]` floor so they never exceed a narrow screen, sit on the `zPopover` rung, and are styled with a glass token (`glassPanel` for the explainer, `glassPopup` for the small dot tooltip) — the dot tooltip was previously a raw `bg-gray-900` `whitespace-nowrap` box that both broke the monochrome-glass look and could run off-screen.

## Sticky chrome must not stack (heights are measured, composition is manual)

Up to three horizontal bars can pin to the top of the events area — the app-level **draft bar**, the **Events/Members tab switcher**, and the events **select/filter toolbar** — plus the floating month selector. They must never paint over one another. Heights are tracked **dynamically**: the draft bar and tab bar are measured with `ResizeObserver`s (`draftBarHeight`, `tabBarHeight`, reported 0 when a bar is absent, e.g. the draft bar when there are no uncommitted changes), and lower bars are offset by the measured sum — the tab switcher pins at `top: draftBarHeight`, and the select toolbar gets `stickyTop = draftBarHeight + tabBarHeight`. What is **not** automatic is the *composition*: which bars stack in which order is wired by hand (each consumer decides its own `top`), because the set of simultaneously-sticky bars is small and view-specific. Rationale: hard-coding pixel offsets broke whenever a bar's content wrapped to two lines; measuring each bar keeps the stack correct across breakpoints and content changes, while keeping the ordering explicit avoids a general-purpose layout framework for three bars. Related: toasts sit at `bottom-20` (not `bottom-4`) so the transient generation toast doesn't cover the floating month selector.

## The draft bar is deliberately app-level, not scoped to the Events view

Although every uncommitted change is currently an *event* change (the draft only tracks events — see [data-layer.md](data-layer.md)), the unsaved-changes Save/Discard bar is rendered as top-level app chrome rather than inside the Events column. Rationale: it is the app's single "publish" control and must stay visible/pinned regardless of which tab (Events vs Members) or split-pane is focused; scoping it into the Events view would hide it exactly when a user switches away mid-edit. This is revisited if non-event fields ever join the draft.

## Events lead over Members (binding)

Events and Members are shown **one at a time via a tab switcher at every breakpoint** — there is deliberately no side-by-side split view, even on wide screens. **Events come before Members** and `activeTab` defaults to `'events'`. Rationale: the primary task is building the roster (an events-centric activity); the members list is reference/support data, so it should never compete with events for horizontal space. A prior desktop layout showed the two panels side-by-side (Events in a wider `lg:w-7/12` column); it was dropped in favour of one consistent "separate tabs" default so the roster-building surface gets the full width on every device and the layout behaves identically across breakpoints.

## The Auto (generate) button is a floating FAB with an on-demand explainer

The Auto (generate) button is a floating FAB, not a top-bar button, and its algorithm explainer is **on-demand**: the full write-up lives in `AlgorithmDescriptionModal`, opened by clicking the FAB's hover card — not shown inline — to keep the toolbar uncluttered. Generation itself runs immediately with no confirm gate or result modal (see [events-ui.md](events-ui.md)).

All floating buttons share one bottom-right column (`fixed right-4 bottom-safe`, `flex flex-col items-end gap-2`) built from the `GlassFab` primitive at a uniform `h-12 w-12`: Auto (generate), Undo, Redo, the `{ }` YAML editor, and a **dual-purpose scroll button**. That last FAB is appended **last** (bottom-most, most thumb-reachable) and **toggles by scroll position**: once the window is scrolled past ~half a viewport (`window.scrollY > innerHeight * 0.5`) it is a **scroll-to-top** button (chevron-up, smooth scroll to `top: 0`); at the top of the page it becomes a **jump-to-today** button (calendar icon) that smooth-scrolls to the first event card **on or after today**. Jump-to-today only appears on the **Events** tab (there are no event cards on Members); it works by querying `[data-event-date]` cards (rendered in chronological DOM order) and picking the earliest whose `YYYY-MM-DD` is `>= ` today's local date, falling back to the last card if every event is past. It scrolls **manually** (not `scrollIntoView`) to `card.top + scrollY − (draftBarHeight + tabBarHeight + gap)` so the target lands **below the sticky header stack** (pinned draft bar + tab bar), not hidden behind it. The page scrolls on the window (`min-h-screen`, no inner scroll container). The whole FAB column is hidden while the YAML drawer is open.
