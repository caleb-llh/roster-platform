# Events view interactions (binding spec)

Binding rules for the Events view: manual swap validation, bulk-clear + select
mode, selection scales, exports, and generation UX. UI styling tokens are in
[design-system.md](design-system.md).

## A role may occupy more than one slot in an event (duplicates are first-class)

The roster is a **positional array** (`event.roster[] = [{ role, member_id }, …]`) addressed by index, so the *same* role can legally appear in multiple slots of one event — e.g. two `roving-cam`. This is intentional and every index-based feature already supports it (diff/`computeRosterDiff` keys by `date`+`roleIndex`, swap/move by index, bulk-clear by index, generation fills each slot independently). Two rules keep the rest of the UI consistent with this:

- **Availability is computed per role, not per slot.** `getAvailableMembersForEvent` keys its result by role name and computes each role's candidate list **once** — who *can* fill `roving-cam` is identical no matter how many `roving-cam` slots exist, so the Availability-Details breakdown shows the role a single time. **But `assigned` must reflect *any* slot of that role:** the helper pre-indexes the member_ids assigned to each role (a `Set` per role) so a member covering the *first* of two duplicate slots is still marked assigned. **Bug fixed:** it previously set `assigned` per-assignment while keying by role name, so the second slot's occupant overwrote the first and only the last duplicate showed as assigned (green). Regression-tested in `constraintPrimitives.test.js`. The per-candidate **`available`** flag comes from the shared `availability` **constraint descriptor** (one authority — the same rule the generator/validator/swap use), called directly so unavailability always shows as a cue regardless of the enforcement flag; role capability stays the UI `canFillSlotRole`/promotion rule. The dropdown is thus a **feasibility consumer** of the registry — see [generation.md](generation.md#hard-constraints-one-authority-many-consumers).
- **The "+ Role" menu offers every role, even already-used ones.** It deliberately does *not* filter out roles already present in the event (it used to), because duplicates are first-class; blocking them in the one manual-add path while generation/data could still produce them was an inconsistency.

## Manual swap validation must ignore the slot each member is *leaving*

Manual drag-and-drop / swap validation lives in the pure `explainSwap` helper (`swapPolicy.js`), consumed by the Session `swap` **command** ([session.md](session.md)) — the one command that HARD-rejects — and unit-tested directly; `canSwapRosterSlots` is a thin boolean wrapper over it (`explainSwap(args).ok`) kept for call sites that only need the yes/no. It checks, for each member landing in its new slot: role compatibility (full performer, or a promoted trainee for a real role), availability on the destination date, once-per-event (no duplicate member in one event), and no time clash (the member isn't already in another event whose span overlaps — ignoring the event they're vacating in this swap). On rejection it returns `{ ok: false, reason }` where **`reason` is a specific, human-readable sentence naming the member and cause** — e.g. `"Alice can't fill the vm role."`, `"John is unavailable on 2026-02-15."`, `"Jane is already rostered on 2026-02-08."`, `"Bob is already rostered on an overlapping event (2026-02-08)."`, or `"Bob is inactive and can't be assigned."` — and the invalid-swap toast shows that sentence verbatim. Rationale: the old toast was a single generic line ("…would break role, availability, or once-per-event rules") that made the user guess *which* rule and *which* member tripped; surfacing the first failing check by name tells them exactly what to fix. The reason is produced in the pure helper (not the component) so it is unit-tested alongside the boolean outcome. The once-per-event check **must ignore the index each member is vacating within the event being checked**: for a same-event swap the two slots share one `roster` array, so testing memberA→slotB ignores `sourceIndex` and testing memberB→slotA ignores `targetIndex`; for a cross-event swap the incoming member vacates nothing in the destination event, so ignore nothing (`-1`). **Bug fixed:** a same-event, different-role swap (e.g. moving a member from `vm` to an empty `cam-1` in the same event) was rejected because the check ignored the *source* index for both members, so memberB (or the member's own still-present entry) tripped the duplicate clash. Extracting the logic into a tested pure helper locks this in. `explainSwap` enforces only the **feasibility** rules (role, availability, once-per-event, no-clash), *not* the load/cadence caps (week/month, understudy gate) — a manual swap may deliberately override those; this subset is intentional, see [generation.md](generation.md#hard-constraints-one-authority-many-consumers).

## Bulk-clear of assignments: clear members, keep slots, one undo step

The Events view has a multi-select mode. Its bulk action **clears the assigned member from each selected slot but keeps the role slot** — it reuses the same non-destructive semantics as clearing a single slot (the `assign` command with `memberId: null`), *not* the destructive "remove whole role slot" path (`removeSlot`). Rationale: the common need is to wipe a batch of (often auto-generated) picks and re-fill them, so the role requirements must survive; deleting role slots wholesale is a different, rarer operation kept separate. The mutation is a pure helper, `buildBulkClear(events, keys)` (`bulkClear.js`, unit-tested), which drops the `isGenerated` tag on cleared slots and ignores empty/unknown keys so the count never lies; it is wrapped by the Session `bulkClear` **command** ([session.md](session.md)). The whole selection is applied in **one** draft edit → a single draft entry and a single undo step, plus one log line (`Cleared N assignments`).

**Two ways in: a gesture on a pill, or an explicit Select button (binding).** You can enter select mode by **long-pressing (touch, ~500ms)** or **right-clicking (desktop `contextmenu`)** a filled assignment pill, which enters with that pill pre-selected (`enterSelectAt(key)`); or by clicking the **Select** button in the Events header, which enters with an empty selection (`enterSelectAt(null)`). The button is deliberately **not sticky** — it lives in the normal header row and is simply *replaced* by the sticky selection toolbar once select mode is active, so there is never a second bar competing for the sticky stack. The button coexists with the gestures: the gestures were the original discoverable-on-the-pill path (an earlier buried ⋮-menu item was removed as too indirect), but a labelled top-right affordance makes "I just want to start selecting" obvious, especially before any pill is chosen. Left-click (opens the picker) and left-drag (swap) are deliberately untouched, so the enter-select gestures don't collide with them; the long-press timer cancels on `touchmove`/`touchend` so a scroll or drag never triggers it.

**Selection works at three scales, all scoped to the visible/filtered events.** (1) *Slot* — click/tap a pill toggles it; **Shift-click** extends a contiguous range over the visible order (desktop). (2) *Event* — a tri-state checkbox in each event-card header selects/deselects all filled slots in that event. (3) *Month* — the same tri-state checkbox in each month header does so for the month. Plus the toolbar's **All** / **Generated** / **Unselect all**. Everything is computed from `filteredMonths` (the ordered `visibleFilledKeys` flat list powers "All" and the range; `eventFilledKeys`/`monthFilledKeys` power the group checkboxes), so "select all/visible" is consistent with how export treats "everything". Group toggles are a predictable tri-state: if every key in the group is already selected they deselect, otherwise they select (`toggleSlotBatch`). Only **filled** slots are ever selectable (an empty slot has nothing to clear); the group checkboxes and per-pill toggle render **only in select mode**, so the normal view stays uncluttered.

**Why buttons/checkboxes, not a drag-marquee:** a rectangle lasso is unreliable against a responsive wrapping card grid across month sections and unusable on touch (the primary target), whereas long-press entry + group checkboxes + shift-click ranges deliver both "select everything quickly" and precise picking without any always-on chrome.

## Export column order (real roles first, understudies last)

The CSV / "Copy to Excel" exports use the shared column layout (`exportColumnLayout` in `EventsView.jsx`). Columns are ordered **metadata → all real roles → all understudy columns**: date, day, reporting time, event name, then every real role (in catalog order, duplicates numbered e.g. `roving-cam 2`), then every `X-understudy` column at the end. Rationale: an understudy column right after each real role interleaved trainees with performers and made the "who is actually rostered vs. who is shadowing" split hard to scan; grouping the understudy columns at the end matches how the roster is read (performers first, understudies as a trailing block). **Missing slots render `-`** (not blank) in the exports so an empty cell is unambiguous. (An on-screen Table view previously shared this layout but was removed as unused — the card view is the only on-screen presentation.)

## Generation runs immediately — no confirm gate, no result modal

Clicking Auto generates straight into the draft; there is **no pre-generation confirmation dialog** and **no post-generation result modal** (the old `GenerationResultModal` was removed). Feedback is the transient toast (what this run filled — see [design-system.md](design-system.md)) plus the live stats panel and inline diff dots. Rationale: generation is **undoable** (it lands in the draft, behind Save, and on the undo stack), so a modal gate added friction to a reversible action; the algorithm explainer is available on demand from the FAB hover card for users who want the details before running.

## Past events are muted (relative to today)

An event card whose date is **strictly before today** is dimmed (`opacity-50`) so the eye is drawn to upcoming events. "Today" is read at **render time** from the client clock (local midnight), so the muting reflects the actual current date without any stored state — reload on a new day and yesterday's events dim automatically. The comparison is **day-granular**: a same-day event is *not* past (it stays full-opacity through the day it happens). The event date is parsed at **local** midnight from its `YYYY-MM-DD` parts (not `new Date(str)`, which is UTC) so the boundary can't slip a day in a negative-offset timezone — the same parsing invariant used by the member-availability calendar (see [design-system.md](design-system.md)).

## Member-availability heatmap (roster stats)

The roster-stats panel's Details section shows a **role × event-date availability heatmap** (`AvailabilityHeatmap` in `distributionUtils.jsx`, fed by the pure `computeAvailabilityByRole` in `availabilityUtils.js`, unit-tested). It is rendered **first in the Details section — above `QualityMetrics` (Shift Distribution etc.)** — since "can I field these dates at all" is the primary planning question. Binding semantics:

- **Grid = roles (rows) × unique event dates (columns)**, dates chronological. Constraints are date-based, so events are the natural sample points; there is no interpolation onto empty calendar days, and multiple events on the same date **collapse to a single column** (both availability and required-slot counts sum/aggregate over that date).
- **A member counts as "available for role R on date D"** when they are included (`include !== false`), can **fully perform** R (`canFillSlotRole` — a trainee who only *understudies* R is **not** counted), and is **not** marked unavailable on D. This chart is a **deliberate non-consumer** of the `CONSTRAINTS` registry: it measures bench depth ("how many *could* I field"), ignoring who is already assigned, specific slots, and all caps — so it uses the shared `canFillSlotRole`/`isMemberUnavailable` primitives directly rather than the placement-oriented registry (see [generation.md](generation.md#hard-constraints-one-authority-many-consumers)).
- **Cell colour encodes coverage** (`available` vs. `required`, where *required* is the number of slots for R across that date's event(s)), on a **roster-normalized** scale (see `availabilityCellColor`). Hard floors apply first, independent of the roster: **red** (muted) = short (`available < required`) or exactly enough (`available === required` — coverable but zero cover if anyone drops); slate = "no demand". For the remaining cells with **real slack** (`available > required`), the colour is a **continuous monochrome (single-hue slate) ramp** that **deepens** (lower lightness) as the cell's coverage ratio `available/required` falls within the roster-wide **min/max slack-ratio range** (`scale`) — i.e. among the still-coverable cells, **darker = thinner bench = more concern**. Hovering a cell shows a glass tooltip with available / required / slack. The heatmap has **no helper caption** — the legend row carries the whole colour key.
- **Why monochrome slate, not a two-hue gradient:** an amber→emerald ramp read as two competing colours and fought the app's subdued palette. The ramp reuses the **same slate hue** as the sibling roster-stats distribution bars, varying only in lightness ("deep ⇒ pale = more comfortable cover"), so the heatmap sits consistently alongside its neighbours, while the reserved (muted) **red** — the only other hue — remains unambiguous as the danger signal.
- **Why roster-relative scale, not a fixed ratio:** a fixed "green ⇒ ≥ 2× demand" rule still painted an abundant roster almost entirely green (availability dwarfs the small per-event demand), while a differently-staffed roster could show none. Anchoring the gradient endpoints to *this* roster's own **min/max** slack ratios makes the chart answer "which of my dates/roles are comparatively thin" regardless of absolute headcount. The scale is taken over **slack cells only** (short/exact excluded so reserved-red cells don't stretch the healthy ramp) and **globally across all roles** (one shared scale, never per-role — per-role normalization would manufacture a cool colour for a role that is always comfortable).
- **Real roles only**: understudy slot roles are excluded to keep the grid readable.

Rationale — **why a heatmap, not a line chart:** the first version was a multi-line "available per role over time" chart. With several roles it became unreadable spaghetti (roles that track each other overlap; the per-event saw-tooth reads as noise; and lines falsely imply continuity between discrete event dates). A grid gives each role its own row (scales to many roles), treats dates as the discrete points they are, and — by colouring **slack** rather than raw availability — makes the actual planning signal, *where am I short*, pop out as red cells. Encoding slack also folds in demand (required slots) for free, turning "how many could I field" into "can I actually fill this".

## Compact quality metrics intensity semantics

The compact `QualityMetrics` section in the roster-stats panel uses **darkness as "cause for concern"** across its secondary visuals:

- **Time Spacing dots:** darker dots mark assignments whose **nearest neighboring shift is closer** on the roster timeline. Their intensity is normalized across the **currently visible set of dots**, so the panel uses the full contrast range instead of washing everything toward the same middle tone; medium spacing differences remain distinguishable rather than every dot reading as similarly intense.
- **Shift Distribution bars:** taller bars still encode **how many members** share a shift count, but the bar fill darkens as the **shift count itself** rises across the chart — the right side of the distribution is visually heavier because "more shifts on one person" is the concern being scanned for.
- **Role Rotation Quality bars:** bar **width** still encodes the rotation ratio (`distinct members ÷ shifts`), but the color is now one **shared full-track dark→light gradient** for every row. In other words, every bar starts from the same left-edge intensity; normalization to the **full track width** means only **how far across the shared gradient the fill reaches** changes. This avoids the earlier bug where a short bar looked like a compressed copy of the whole gradient.

This keeps the panel's micro-visuals aligned: red = actual defect / shortage, while within the slate-only comparisons, **darker means "pay more attention here."**

The compact charts also use a **consistent glass-card treatment**: Member Availability, Shift Distribution, Time Spacing, and Role Rotation each sit inside the same `glassCard` framing, and each section title lives **inside its own card well** rather than floating above it. Divider lines between the sections are not used; the repeated card wells provide the visual grouping instead. Time-spacing dots keep a thin border so even the palest dots remain legible against the glass panel.

Across the roster-stats visuals, the **maximum slate intensity is aligned to Member Availability**: the deepest availability cell, the darkest time-spacing dot, and the darkest bar all stop at the same muted deep-slate endpoint rather than the secondary charts using a darker maximum than the heatmap.
